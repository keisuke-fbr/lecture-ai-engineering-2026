## 演習

- 第1回（素のLLM）とエージェントの回答の違い：
  同じ質問「AIE2026の講座の宿題にある「3レベル」とは何ですか？」で比べた。
  第1回の `app.ask` は、講座の情報を持たないため、AIの活用レベルや課題の難易度など複数の可能性を並べ、最後は Slack や講師に確認するよう案内して、答えを特定できなかった。
  エージェントは用語集を検索してから答え、宿題の3レベルは基礎・実装・発展で、どれか1つに取り組めば完了だと正しい内容を断定できた。回答の最後には「第1回」と関係する回も付いた。
- `--trace` で見えたツール呼び出し（ツール名と引数）：
  - 「LoRAとQLoRAの違いは？」では、`search_glossary` を query が `LoRA` と `QLoRA` で2回呼んだ。用語を1つずつ別々に検索していた。`search_glossary` の docstring に「query には調べたい用語を1つだけ入れる」と書いてあるため。
  - 「3レベル」の質問では、`search_glossary` を query が `3レベル` で1回呼んだ。
  - 「第2回の内容から確認問題を1問出して」では、`make_quiz` を lecture が `2` で1回呼んだ。
- 1つの質問での LLM 呼び出し回数 `requests`：
  - LoRAとQLoRAの質問は2回。ツール呼び出し2回を並べて行い、結果を受けて回答を作った。
  - 3レベルの質問は2回。ツール呼び出しは1回。
  - 確認問題の質問は2回。ツール呼び出しは1回。
  - ツールを呼ぶ質問は、ツールを呼ぶ段階と、結果を見て回答する段階で、LLM を2回呼ぶ形になっていた。
- 追加したツールと、docstring に書いた説明：
  `app/tools.py` に `make_quiz` を追加し、`app/agent.py` で `agent.tool_plain` を使って登録した。引数は lecture（整数）、返り値は文字列。
  docstring は「指定した回の用語から1つを選び、確認問題と答えを返す。『第2回の確認問題を出して』のように、復習用の問題を求められたときに使う。lecture には回の番号（1始まりの整数）を入れる。」。
  用語集から lecture が一致する用語を集めて `random.choice` で1つ選び、question と answer を持つ JSON 文字列で返す。question は「○○の意味は？」、answer は用語の definition。該当する用語がない回は「第99回の用語は用語集にありません。」のように返す。
  確認結果：`--list-tools` に `make_quiz` と docstring が表示され、`--trace` で `make_quiz` が lecture=2 で呼ばれ、`uv run pytest -q` は 15 passed だった。

## 宿題

- 取り組んだレベル：発展の b。Pi のシステムプロンプトと自分の `INSTRUCTIONS` を比べる
- やったこと：
  - Codespaces で `npm install -g --ignore-scripts @earendil-works/pi-coding-agent` を実行して Pi を入れた。
  - GitHub の `packages/coding-agent/src/core/system-prompt.ts` を読んだ。このファイルはプロンプトの文章ではなく、プロンプトを組み立てる関数が書かれている。
  - 文章の実物は、インストールした Pi の関数 `buildSystemPrompt` と、ツールごとの説明である `dist/core/tools/` の snippet と guidelines を呼び出して組み立てて確認した。既定のツール read / bash / edit / write で、指示ファイルとスキルなしの状態で組み立てた。`pi` を起動して対話はしていない。
- 結果：Pi のシステムプロンプトは、タグで区切った次のセクションからできていた。

  | セクション | 書かれていること |
  |---|---|
  | 冒頭 | 役割は1文だけ。pi の中で動くコーディングアシスタントで、ファイルを調べ、コマンドを実行し、コードを修正するのを手伝う |
  | tools | 使えるツール4つと、1行の説明 |
  | rules | ツールの使い方のルールと、回答は簡潔に、ファイルパスをわかりやすく示す、という2つ。ツールのルールは、cat の代わりに read を使う、edit は一意に一致する短い範囲で行う、write は新規作成か全面書き換えだけに使う、など |
  | docs | Pi 自身のドキュメントの場所と、話題ごとの対応表 |
  | cwd | 作業ディレクトリ |

  自分の `INSTRUCTIONS` との違い：
  - Pi は、役割の説明が短く、ほとんどがツールの使い方のルール。`INSTRUCTIONS` は、ふるまいのルールが中心で、必ず用語集を確認する、推測で断定しない、宿題の答えは書かない、最後に回を示す、といった内容。
  - Pi には、承認や安全に関する指示がない。確認なしで動く、という説明と合っている。`INSTRUCTIONS` にも安全の指示はない。
  - Pi には、ツールの使い分けと、自分自身のドキュメントの場所の案内がある。`INSTRUCTIONS` にはない。
  - Pi は、指示ファイルやスキルをあとから差し込める設計になっている。`INSTRUCTIONS` は固定の文字列。
- 気づき・疑問：
  - 工夫として、Pi は全部を書かず、目次を渡して必要なときに読みに行かせている。拡張機能、テーマ、スキル、キー割り当て、SDK、MCP などの説明は、システムプロンプトに全文を入れていない。docs セクションに「話題とファイルの対応表」だけを載せ、たとえば拡張機能なら docs/extensions.md、MCP サーバーなら docs/mcp.md としている。そして、ユーザーがハーネス自体について尋ねたときにだけ読むよう指示している。モデルは、聞かれたときだけそのファイルを read で読みに行く。毎回のプロンプトが短くなり、使わない説明で文脈やコストを使わずに済む。
  - 自分のエージェントに応用するなら、`get_lecture_summary` がすでに近い形になっている。各回の要点を全部 `INSTRUCTIONS` に入れるのではなく、回の番号を引数にして必要な回だけを読みに行かせている。`INSTRUCTIONS` が長くなってきたら、この形にして減らせる。
